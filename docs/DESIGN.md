# FerrumGate 架构设计

FerrumGate 是面向家庭网络、NAS 和小型服务器的 Rust 自托管网关。交付入口为 `fgate`，业务面负责代理流量，未来的管理面负责修改期望状态。优先交付文件配置、可验证的代理和 HTTPS，再逐步增加 Web UI 与可选模块。

执行阶段、命令和验收见 [EXECUTION.md](EXECUTION.md)。贡献规范见 [AGENT.md](AGENT.md)。

## 1. 上游基线与兼容性范围

以 2026-11-25 的 Gately README、Web 服务文档和模块清单为功能参考，上游 `main` 当时为 `442162e4d0b64df119bc5fe6469a088adee844c4`。实际迁移工作开始时，冻结一个上游 tag 或提交以及脱敏导出样本。各模块的配置格式、默认值和行为由该版本的样本与测试确认。FerrumGate 使用独立 TOML schema 和自有界面。上游仓库标注 Apache-2.0，未来若复用上游实现或资源，需要核对其适用许可及署名义务。[Gately](https://github.com/wangwanjie/gately) · [Web 服务](https://gately.cn/en/docs/modules/web) · [模块清单](https://github.com/wangwanjie/gately/blob/main/modules.json)

## 2. 实施边界与组件

Cargo workspace 使用 Rust 2024 和 resolver 3。Tokio 驱动网络与信号，Hyper 提供 HTTP 编解码，hyper-util 提供共享上游连接池。Serde/TOML 严格加载配置，ArcSwap 发布包含路由、TLS 和上游连接池的只读运行快照。核心自有 Rust 代码禁用 `unsafe`。Axum 可用于未来管理 API。TLS 采用 rustls，优先选可复现构建并通过目标矩阵的密码学提供方。

```text
配置文件 → 读取上限 → 反序列化 → 校验和编译 → 原子发布运行快照
                                                 ↓
客户端 → TCP 接入 → Hyper → Host / path → 代理 → 连接池 → 上游
```

根包 `ferrumgate` 生成 `fgate`，处理命令行、运行时和日志初始化。`crates/fg-gateway` 承担配置和数据面逻辑，对根包只暴露 `check_config` 和 `serve`。包内按 `config`、`proxy`、`server`、`tls` 和 `websocket` 划分。根 workspace 共享锁文件、构建目录和公共依赖版本。后续拆分依据实际编译、权限或复用需求，新增可选能力由消费它的 crate 声明 feature，根二进制负责组合。

## 3. 阶段 A 数据面契约

### 配置

一次服务启动使用一个 TOML 文件，`schema_version = 1` 必填。命令行通过 `--config` 选择文件。运行参数位于可省略的 `[server]` 表。在所有配置层拒绝未知字段。读入上限 1 MiB，最多 1024 条路由和 2048 个后端条目。配置错误只输出字段或索引，避免输出配置值。配置例见 [ferrumgate.example.toml](../ferrumgate.example.toml)。

| 字段 | 默认值 | 约束 |
|---|---|---|
| `server.listen` | `127.0.0.1:8080` | IP 和端口；服务在显式配置时接受外部绑定 |
| `server.tls` | `false` | `true` 使用 TLS 监听，需要证书 |
| `server.tls_handshake_timeout_ms` | 5000 | 1–300000；从开始处理 TLS 握手起计时 |
| `server.max_connections` | 1024 | 1–65535 |
| `server.header_timeout_ms` | 5000 | 1–300000 |
| `server.connect_timeout_ms` | 2000 | 1–300000；单次上游 TCP 连接预算 |
| `server.response_header_timeout_ms` | 30000 | 1–300000；覆盖解析 DNS、连接、TLS、上传等待和上游响应头 |
| `server.connection_lifetime_ms` | 300000 | 1–86400000；从接受连接起计时 |
| `server.shutdown_timeout_ms` | 10000 | 1–300000 |
| `routes[].host` | 必填 | 精确 ASCII DNS 名或 IP，或含一个 `*` 的 DNS 规则，均无端口；DNS 大小写不敏感并容许一个末尾根点 |
| `routes[].path_prefix` | `/` | 以斜杠开头；除根路径外无末尾斜杠，无查询 |
| `routes[].upstream_h2c` | `false` | 为 `http://` 上游启用 HTTP/2 prior knowledge |
| `routes[].websocket` | `false` | 为匹配该条路由的请求允许 HTTP/1.1 WebSocket 升级 |
| `routes[].backends` | 可选 | 配置 1–32 个后端，与 `upstream` 二选一 |
| `routes[].upstream` | 单后端形态必填 | `http://host[:port]` 或 `https://host[:port]`，可选末尾 `/`；无认证信息、路径前缀及查询 |

至少配置一条路由。域名优先级为精确匹配、较长通配规则、`*`；通配同长时以配置顺序为准。重复的规范化 Host 与路径组合在校验时报错。HTTP Host 可带端口，路由匹配使用其中的主机名。路径采用最长段边界前缀，`/api` 匹配 `/api` 和 `/api/v1`。匹配读取原始 URI 路径，转发保留路径与查询的编码。下游可接受的 URI 范围与上游归一化方式应一并考虑。若未来同一站点以路径隔离权限，必须在引入策略时收紧该契约。

### HTTP 转发

- HTTP/1.1 监听接受 origin-form 和单一合法 Host。TLS 上的 HTTP/2 路由见 §6。未知网站或路径返回 404。无效 Host、无效请求目标或冲突的消息成帧字段返回 400。HTTP/1.0 返回 505，CONNECT 或当前路由不支持的 Upgrade 返回 501。
- 出口 origin 完全来自已验证配置。上游请求的 `Host` 为配置中的上游 authority。清除客户端的 `Forwarded`、`X-Forwarded-*` 和 `X-Real-IP`，重新写入 TCP 对端地址、原 Host 和访问 scheme。部署在另一代理后时，地址仍为直接对端。
- 双向清理 `Connection` 指定的字段及标准逐跳字段。代理保留端到端语义。仅支持无传输编码或单一 chunked，按照该跳重建 framing。HTTP/1.1 代理丢弃 trailer frames。WebSocket 与 HTTP/2 见 §5–6。参考 [RFC 9110 §7.6.1](https://www.rfc-editor.org/rfc/rfc9110#section-7.6.1) 与 [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112)。
- 请求与响应按 frame 流式传递，利用连接读写反压，不缓存整包。连接池闲置保留每 origin 最多 8 条，空闲期限 30 秒。代理不额外重放请求。上游故障返回 502，响应头期限到达返回 504，响应开始后的读写错误终止流。
- 接入主循环确认活跃任务数低于上限后调用 accept；达到上限时连接等待内核队列。HTTP/1 头部缓冲上限为 32 KiB，头部等待设期限。连接最大寿命约束长期占用，也会终止到期的慢上传、下载和持续连接。应用层带宽/请求体配额与精细化空闲超时在阶段 C 增加。

### 生命周期

启动时先校验完整配置，完成监听绑定后记录就绪日志。Unix 接收 SIGHUP 后重新读取和校验，单次发布完整运行快照。整个 `[server]` 表视作启动参数，变更需重启。已开始的代理请求使用已选上游。同一持久连接上的下一次请求获取新快照。新快照使用新的连接池和 TLS 配置，已开始的 TLS 会话保留原握手结果。错误候选仍保留在线快照。文件应在同一目录写入新文件后原子替换。SIGINT、Unix SIGTERM 停止接入，连接进入优雅关闭，随后按期限取消剩余任务。

## 4. 阶段 B 手动 TLS

`[server] tls = true` 让单个业务监听器使用 TLS 1.2 或 1.3，HTTP 明文与 HTTPS 使用两种独立启动配置。精确 HTTPS 路由须有覆盖其域名的 `[[certificates]]`，字段为 `host`、`cert_file`、`key_file`。域名须匹配叶子证书 SAN，证书文件按叶子到中间证书排序，密钥文件提供一把 rustls 支持的 PEM 私钥。rustls 验证叶子证书的解析、SAN 及密钥匹配。签发链完整性和当前有效期由 TLS 客户端校验。先选精确 SNI 证书，随后尝试覆盖单个子域标签的通配证书。通配证书的 SAN 必须包含配置的名称。未知 SNI 会在握手时被拒绝。无 SNI 时先选与 TCP 连接本地地址匹配的有效 IP 证书，否则选择有效期结束最晚的 IP 证书，HTTP authority 限于该证书声明的地址。没有匹配证书时拒绝握手。无 SNI 的 IP 路径禁用会话恢复。TLS 下的 Host 需与 SNI 一致，否则返回 421。

外连 HTTPS 验证证书链和目标名称。默认信任 `webpki-roots` 的根证书集。根字段 `upstream_ca_file` 可追加私有 CA，添加后对当前所有 HTTPS 上游生效。指定的 TLS 文件相对配置文件目录解析，每个文件最多 1 MiB。Unix 热加载以一代提交路由、证书和上游信任配置。使用带版本的证书和密钥文件名，再替换 TOML。TLS 配置示例和轮换命令见 [EXECUTION.md](EXECUTION.md)。

### ACME HTTP-01

启用 `[acme]` 后，由独立明文监听器服务准确匹配 Host／token 的临时路径。一个配置管理最多 20 个标识的 SAN 证书。HTTP-01 支持精确 DNS 名和 shortlived 档位的 IPv4／IPv6 标识，DNS-01 支持精确与通配 DNS 名。ACME 账户与证书私钥分别持久化在私有状态目录，目录锁防止并行写入。组合 PEM 同目录替换并同步后再发布到共享 SNI 选择器；配置热加载继续引用同一管理状态。管理设置发生变化时重启。

有效证书在重启时复用。指定 `acme.profile` 后，订单必须确认该 profile。证书档位和私钥随同一身份文件提交。重启时发现档位变化则立即申请新证书，并保留旧证书直到切换完成。签发和续期检查密钥配对、SAN 和有效时间。无 SNI 路径可使用 ACME 安装的 IP 证书，含多个 IP 的托管证书只接受这些地址作为 HTTP authority。归档账户在 CA 目录及邮箱一致时重用。首次注册可通过私有文件读取 EAB 密钥，密钥与归档账户分开保存。终止时取消监听器与后台任务。证书和账户状态可跨重启恢复，单个未完成订单的恢复留待后续。 [Gately 证书模块](https://gately.cn/en/docs/modules/ssl)

### ACME 本地部署

本地部署工作单独等待证书代更新，定期校验输出。它以私有目录锁序列化写入，限定部署目录仅供原属 ACME 状态使用。新证书与私钥写入同一代，文件及目录同步后原子切换指针，并保留上一代。外部路径冲突和发布错误保留内部在线证书。

### ACME DNS-01

启用 `[acme.dns01]` 后使用 Cloudflare 托管区、私有 API 令牌和指定 DNS 递归解析器。可配置明确区域，或通过挑战最终落点的 SOA 和 Cloudflare Zone Read 自动选择唯一的活动区域。DNS-01 支持精确及通配 DNS 名，验权通过 TXT，只启动业务 TLS 监听。通配证书仅覆盖一个 SNI 标签，精确证书优先。

DNS-01 默认沿 CNAME 查找最终 TXT 名称，最多支持八跳。随机同级名称出现相同 CNAME 时，保留原挑战名以避开通配记录产生的别名。实际写入名称必须属于配置或发现的区域。每条 TXT 在写入 Cloudflare 之前记录名称、值和随机归属标签，写入时记录所属区域，获得记录 ID 后再持久化一次。提交挑战前从 DNS 读取实际 TXT。清理前复核名称、TXT、归属标签与 ID。创建结果不确定时按归属标签查询。清理错误保留日志状态，在进程或证书恢复后重试。 [Gately DNS-01](https://gately.cn/en/docs/modules/ssl#dns-01-validation) · [Cloudflare Create DNS Record](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/create/) · [Cloudflare Delete DNS Record](https://developers.cloudflare.com/api/resources/dns/subresources/records/methods/delete/)

## 5. 阶段 C1 WebSocket

命中精确 Host 和路径规则后，`websocket = true` 允许 HTTP/1.1 GET 升级。网关校验 `Connection`、`Upgrade`、版本 13、16 字节握手 nonce 和请求体边界。每一跳重建 Upgrade 头，保留 `Origin` 供上游执行来源策略，并按配置验证 HTTPS 上游。上游返回 101 时，网关再核对升级类型、握手证明和已选子协议。握手请求无效返回 400，上游 101 不符合契约返回 502，上游普通拒绝响应按 HTTP 路径透传。该阶段停用 WebSocket 扩展协商。SHA-1 仅用于 RFC 6455 规定的握手证明。[RFC 6455 §4](https://www.rfc-editor.org/rfc/rfc6455#section-4) · [Hyper Upgrade](https://docs.rs/hyper/latest/hyper/upgrade/index.html)

成功后两端共享一条双向字节转发任务，使用有界缓冲并透传文本、二进制和控制帧。升级保持原连接的并发名额和寿命预算。服务停止或达到寿命期限时关闭两端连接。端点正常发出的 Close 帧照常通过。重载后已升级会话继续使用握手时的上游，新的升级请求读取新快照。

## 6. 阶段 C2 HTTP/2 与原生 gRPC

TLS 监听器公布 `h2` 和 `http/1.1` ALPN，明文入口使用 HTTP/1.1。HTTP/2 按 `:authority` 路由，要求 `:scheme` 为 `https`，同时提供 Host 时必须与 authority 一致，站点身份仍与 TLS SNI 绑定。服务端每连接最多 100 条并发流，设置 32 KiB 头部列表、65,535 字节流窗口、1 MiB 连接窗口及 64 KiB 每流发送缓冲。连接寿命与停机预算仍由监听器管理。

HTTPS 上游自动通过 ALPN 协商。HTTP 明文上游可在路由显式设置 `upstream_h2c = true`，使用 HTTP/2 prior knowledge 连接池。WebSocket 升级使用独立 HTTP/1.1 池，可与 h2c 共用一个支持双协议的上游地址。入口 HTTP/2 的普通请求可转为 HTTP/1.1 上游请求。原生 gRPC 要求入口及上游均为 HTTP/2，后端不提供适配协议时返回 502。

原生 gRPC 的请求和响应按 frame 流式转发，HTTP/2 两端之间保留业务 trailers 与 gRPC 状态。逐跳、成帧、凭据和转发身份相关字段按网关策略过滤。HTTP/2 取消由协议库向对应上游流传播。gRPC-Web、明文 HTTP/2 入口及 HTTP/2 扩展 CONNECT 留待后续。[Gately 后端设置](https://gately.cn/en/docs/modules/web) · [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113) · [gRPC HTTP/2 协议](https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md)

## 7. 阶段 C3 多后端和被动摘除

同一路由按权重轮询可用主后端。权重为 1–100，缺省为 1。全部主后端处于冷却期时，才按权重挑选备用后端。编译配置时校验至少一个主后端，并按 scheme、规范化主机和有效端口拒绝重复 origin。原有 `upstream` 单后端写法仍可使用。

多后端路由按配置快照保存独立的被动状态。后端连续三次出现连接故障后暂停选择 30 秒。期限到达后恢复参与选择，下一次收到响应头清除故障状态。导致摘除的请求仍返回 502，后续请求重新选择；全部后端冷却时返回 503。单后端保持原有错误语义。新配置代重新建立后端状态，已选上游的请求继续绑定原配置。主动探测可通过 `[routes.health]` 开启。按请求安全重试仍有独立验收。[Gately 后端权重、备用与健康检查](https://gately.cn/en/docs/modules/web#backends-weight-and-backup)

### 主动健康检查

HTTP 模式发送 GET，按小于 400 的响应状态判断结果。TCP 模式只建立连接。HTTP 探测使用该路由的 h2c 配置或 HTTPS 验证。探测默认每 10 秒一次，超时 3 秒，连续失败 3 次摘除，连续成功 2 次恢复。设置主动检查后，由探测确认恢复，单后端也可摘除。每代配置最多 32 个同时执行的探测，重载替换探测任务，停机取消。 [Gately 健康检查](https://gately.cn/en/docs/modules/web#health-checks)

### 本地站点

重定向、固定文本与静态文件使用 `[routes.response]`。三种响应共享 Host、路径和 SNI 验证。静态站点在配置代中持有受限目录句柄。解析 URI 时逐段解码并验证，文件打开受目录能力约束，配置目录与引用的 TLS 文件在启动和重载时检查。并行文件查找上限为 32，磁盘读取按 64 KiB 缓冲流式进行。

### TCP/UDP 端口转发

TCP 与 UDP 分别允许配置至多 64 个监听器。列表及范围保留书写顺序，固定目标端口供整条规则使用，等长列表按位置映射。每个监听器独立应用连接或会话上限，UDP 会话上限还计入进程总预算。

`[[tcp_forward]]` 每规则最多 8 个目标。启动预绑定全部端口，HTTP 可用 `server.http_enabled = false` 关闭。单个目标拨号失败可在转发数据之前切换；建立连接后通过 Tokio 双向复制并保留半关闭。可按规则在应用数据之前向后端写入 PROXY v1/v2，地址来自实际 TCP 对端和本地接收地址。接入名额、单次拨号期限、首次数据期限和总连接寿命按规则限制。首次数据期限在出站连接和 PROXY 头完成后开始，双向等待首字节并保留半关闭。监听、拨号目标与预算属于启动配置，退出时停止接入并复用进程的排空期限。来源规则和路由表共享配置快照，允许原子热重载。TCP 在接入前检查，UDP 在向上游及回给客户端前检查。可为 TCP 启用每源配额和显式 CIDR 豁免。IPv4 按地址、IPv6 按 /64 计数，连接结束或取消时释放配额。

`[[udp_forward]]` 按源 IP 和端口建立独立的已连接 UDP socket。每个监听端口轮询最多 8 个目标。会话在绑定或连接报错时继续尝试剩余目标，建立后固定该目标。无响应由空闲回收处理，已发送的数据报不重发。会话等待上游响应时只等待套接字就绪，收到响应时借用回包缓冲。每个工作线程最多缓存一个 65,535 字节的空闲回包缓冲，正在转发的响应可以临时持有额外缓冲。每会话队列长度为 4 个报文，进程最多保留 1024 个排队或正在发送的报文和 4096 个会话。达到预算丢弃新报文，空闲到期释放会话，停机取消。TCP 和 UDP 可同时使用同一数值端口。

## 9. 性能与运维契约

- 热路径每请求只读取一次路由快照。Host 查询走哈希表，同一 Host 的前缀按长度降序匹配。优先测量在真实站点数量下的开销，确认热点后再考虑 radix tree。
- 复用连接池、避免中间整包缓存和逐请求字符串日志。变更前后用相同后端、协议、连接复用与负载分布，比较吞吐、p50/p95/p99、超时、CPU、RSS 和打开文件数。
- 第一批用生命周期事件和重载状态用于诊断。以 `fgate serve --log-level debug` 启用连接和上游错误日志。转发指标可通过独立回环 HTTP 监听采集，按实际监听地址与协议聚合，最多 640 条时间序列。采集最多并发 16 条连接，请求头限时 3 秒、连接限时 5 秒。启用时使用原子计数，TCP 在成功写入时增加应用字节计数，取消或超时会释放活动计数。关闭采集时沿用原有转发路径。后续 Web 指标按监听器、固定站点标识、响应码族聚合，客户端 IP、原始路径、查询、请求头和密钥不作为标签。
- 发布标准通过实测建立。性能验收先比较同一基线的前后运行漂移，再用 Gately 做语义等价的外部参照。样本分布、硬件、版本和参数写入报告。
- 默认样例运行在回环地址。对外部署可启用手动 TLS 或交由前置终止代理，并配置资源限制。管理面落地后单独验收隔离。平台验收分别记录 Linux、macOS 和其他目标系统的构建及运行结果。

依赖实现参考 [Hyper HTTP/1 服务端](https://docs.rs/hyper/latest/hyper/server/conn/http1/struct.Builder.html) 与 [hyper-util 连接池](https://docs.rs/hyper-util/latest/hyper_util/client/legacy/struct.Builder.html)。版本以提交的 `Cargo.lock` 为准。

## 10. 配置目录存储（WP-00）

`fg-config::ConfigStore` 为每个模块保存一个明文 `<name>.json` 文件。同一存储句柄串行访问磁盘，读取缺失文件返回 `Loaded::Missing`。配置名最长 64 字节，首字符是小写字母或数字，其余字符可加下划线和短横线。配置文件读写上限为 64 MiB，解析错误只报告配置名与行列位置。`save` 使用两空格缩进并补一个换行，`write_raw` 保留传入的字节。

写入先逐字节检查现有内容，再通过同目录临时文件写入、同步、原子替换。Unix 上创建配置目录和临时文件后显式设为 0700、0600，替换和删除后同步父目录。如果父目录同步失败，调用方收到错误，此时替换或删除可能已可见。权限收紧跳过符号链接。读取可解析指向常规文件的符号链接，写入替换链接本身。

`fg-core::fsperm` 在进程内登记打开的配置目录。路径判定考虑路径组件、符号链接和 Unix 文件对象。静态站点在打开发布根时拒绝与配置目录重叠，文件读取继续使用受限目录句柄。配置目录启动参数和权限收紧调用由 WP-03 接入。现有部署使用 `fgate check/serve --config <TOML>`。

### 配置历史、差异与回滚（WP-02）

启用历史后，`ConfigStore` 在同一把锁内保存待覆盖或删除的旧文件。快照流式写入 `history/<name>/<version>.json` 并同步，再发布配置改动。相同内容跳过快照。默认保留常量为 30，调用方可以指定保留数或停用历史。账号、令牌等敏感状态始终排除。版本号是纳秒精度的 UTC 时间戳，同一存储句柄内递增，碰撞时保留已有版本。恢复沿用原子写路径，保留恢复之前的内容。历史写入失败时当前配置仍可用。配置发布之后父目录同步或历史淘汰失败时，变更可能已可见。

行级差异在锁外运行。相同前后缀先裁剪，比较区间最多 4,000,000 个单元格，以单行分数及单元格一位的回溯信息计算。单侧超过 65,536 行时使用多行文本块，限制逐行分配。输出保留变更前后各 3 行上下文。

`rollback-request.state` 是至多 4 KiB 的单槽交接文件。提交只占用空槽，领取通过同目录原子重命名完成。离线恢复支持指定版本及最近一次变更。调用方须确认实例已停机后才离线改写。配置历史的 CLI、管理 API、重启编排和待确认回滚由各自工作包接入。

## 11. 模块框架与注册表（WP-01）

`features.toml` 是模块目录与运行时依赖的来源。Cargo 构建 `fg-core` 时生成包含 27 个模块的目录表。当前构建包含 `webservice`、`ssl` 和 `portforward`。`Registry` 根据已编译模块与关闭列表求出启动集合。`fgate check` 拒绝未知 ID 和仍被依赖的关闭项。`fgate serve` 遇到手工配置的依赖冲突时恢复依赖项并记录警告。TOML 的 `disabled_modules` 缺省为空，已知未编译模块可保留在列表中，修改需重启。

`fgate serve` 编译完整配置并预绑定已启用的监听器，再启动实际运行时。Web 管理 HTTP/TLS 连接和健康检查，证书模块管理 ACME 任务，端口转发模块管理 TCP/UDP 和转发指标。装配层把同一个证书发布句柄传给 TLS 解析器和证书任务。监听器准备失败时释放已准备的资源并退出。

SIGHUP 校验完整候选配置，再一次发布同时包含 Web 路由、TLS 和转发来源策略的快照。SIGINT/SIGTERM 并行停止接入并排空，各模块在同一 `server.shutdown_timeout_ms` 期限内退出。超时后取消剩余任务。管理 API 与配置目录装配分别在后续工作包接入。

## 12. 事件总线（WP-16）

`fg-core::events` 的 32 项目录与固定上游快照的类型名、默认级别和顺序一致。事件按类型初始化级别，发布时补上时间。事件参数遵守项目的凭据保密约定。

发布读取订阅者快照并立即尝试占用有界队列，入口默认 1024 条。获取槽位后才构造事件负载。单个分发任务把同一份 `Arc<Event>` 投递给各订阅者。最多注册 32 个订阅者，每个订阅者拥有一个串行处理任务和 256 条待处理队列。队列满时丢弃该队列的新事件，入口和订阅者丢弃数分别累计。

订阅只收到注册后发布的事件。退订取消当前处理并丢弃排队事件，处理器的 panic 只影响该次投递。最后一个总线句柄释放时取消分发与订阅任务。网关把总线直接交给 Web 运行时，SIGHUP 后继续使用同一实例。主动健康检查发生状态变化时发布 `upstream.down` 或 `upstream.up`，参数为已校验的站点和上游 authority。通知消费者由 WP-68 接入。

## 13. 运行日志基础链路（WP-09）

`fg-logging` 接收现有 `tracing` 事件。按系统、Web、证书和端口转发分别保留内存环形缓冲，默认每组 2,000 条并设有 8 MiB 的估算内存预算。每组序号单调递增。内存与落盘条目只收录允许的结构化字段，来源按名字去重并限于 1,000 项。标准错误沿用原有的 `tracing` 文本格式。

标准错误和磁盘使用独立工作线程与有界队列。等待回显的负载预算为 1 MiB，等待落盘为 4 MiB，队列满时丢弃新条目并回显计数。磁盘正常运行时最长等 1 秒合批，累积到 256 KiB 提前写出。生产者只在短锁内入队。正常退出为两个写入线程共用 3 秒刷新期限。

`fgate serve --log-dir <绝对路径>` 启用 JSON Lines 落盘。Unix 新建目录为 0700，受管理文件为 0600。每组当前文件默认 2 MiB，超过上限前轮转为 `.log.1`。启动恢复两份文件中近期有效记录和 `.sources`，同一日志目录由单进程持有。静态站点的发布根必须和日志目录分离。

### 筛选、查询与导出

`Logs::query` 以序号划分开区间，按序号升序返回最近的匹配记录。`limit = 0` 只查内存，正数上限为 20,000 条，单页最多使用约 8 MiB 内存。常见的内存命中无需打开日志文件。需要补足时，从当前文件和 `.log.1` 倒序按 64 KiB 读块，找到足够记录便停止。查询固定文件句柄、长度与内存序号，合并待写和正在写入的批次，按序号去重。损坏或超长记录会被跳过。

筛选支持级别、来源、关键词短语及排除、IP 与 CIDR、站点、监听器、状态码和时间范围。封禁及管理员隐藏选项读取已有字段标记。`Logs::export` 从旧到新流式写 JSON Lines 或 CSV。CSV 带 UTF-8 BOM，并转义引号、多行内容和潜在公式单元格。磁盘查询和导出由调用方放在阻塞工作线程执行，读取与输出期间释放日志锁。

### Web 归档与清空

通过 `Options::web_archive` 可为 Web 日志启用归档。按 UTC 跨日或达到文件上限轮转，大小取保留预算的四分之一，限制在 1 至 16 MiB。使用 UTC 时间和序号命名归档。后台写盘线程在文件快照锁外压缩，完成并同步后原子发布 gzip，再删除原文件。保留默认 7 天和 32 MiB，Unix 上同时受分区容量 5% 限制，最多保留 128 份历史。启动和轮转时执行淘汰。

查询、导出和重启恢复可读取当前文件、普通轮转及 gzip，仍按序号去重。正序导出流式解压，倒序分页一次最多展开一份 16 MiB 归档。`Logs::clear` 按模块删除当前文件、历史和来源记录，清空内存并记录序号边界。旧待写批次和旧压缩任务无法在清空完成后重新发布。操作前已取得的查询快照仍可读完。

### 日志目录切换与归档时间裁剪

`Logs::set_directory` 先打开目标目录、取得独占锁并读取已有序号。准备成功后原子切换写入队列，新日志从内存和目标目录的最大序号续接，原目录及其已入队记录保持原归属。旧队列最多等待 3 秒刷新，仍在排空时保留工作线程并限制再次切换。传入 `None` 停止落盘，内存与 stderr 继续保留日志。设置入口在切换前须验证目标目录与现有静态站点发布根隔离。

新 gzip 归档的头部保存带校验的最早和最晚 UTC 秒。查询与导出仅在时间范围确定不相交时跳过正文。同一秒内的亚秒边界继续逐条比较。旧归档或元数据无效时使用逐条筛选。
